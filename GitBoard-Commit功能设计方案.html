GitBoard · Commit 提交功能设计方案

版本 v1.3（修订：双视图描述重写 · AI 遵循 .copilot/ 工程指示文件） ·  日期 2026-08-20  ·  基线 GitBoard v0.6.3（engines.vscode ^1.85） ·  参考 Sourcetree「工作副本 / File Status」交互 · GitHub Copilot Language Model API

1. 概述

GitBoard 目前是一个只读为主的提交图可视化工具（fetch / pull / push / reset / checkout 已具备写操作），但日常最高频的动作——暂存与提交——仍需切回 VS Code 源代码管理视图或终端完成。本方案在现有 Webview 内新增一个工作副本提交视图，完整复刻 Sourcetree 的提交流心智模型，并接入 GitHub Copilot 一键生成提交信息。

1.1 目标

  • Sourcetree 级提交体验：文件状态分组（已暂存 / 未暂存）、复选框勾选暂存、选中即看 diff、底部信息栏 + 提交按钮，全程不离开 GitBoard。
  • Copilot 生成提交信息：基于暂存 diff、工程指示文件（.copilot/ 及 Copilot 官方 .github/ 约定，见 §5.7）与仓库近期提交风格，一键（可流式）生成 首行摘要 + 正文，可停止、可重新生成、可编辑。
  • 一步直达、状态不丢（沿用既有产品原则）：工具栏一次点击进入工作副本视图；视图切换、面板隐藏均不丢失草稿与滚动位置。
  • 零新增运行时依赖：git 侧继续走既有 GitExecutor / OpRunner 管道；AI 侧直接用 VS Code 内置 vscode.lm API，不引入任何 npm 包。

1.2 非目标（本期不做）

  • Stash 管理、merge 冲突解决器、交互式 rebase —— 属独立特性，另行立项。
  • 行级（逐行勾选）部分暂存编辑器 —— VS Code 原生 SCM 已擅长，块级暂存（P2）已覆盖八成需求。
  • 提交前 code review / lint 门禁 —— 交给 git hooks。

2. 总体设计

2.1 信息架构：主界面双视图

主界面由两个职能互补的并列视图组成，各自回答一个明确的问题（v1.3 重写描述）：

  • 提交图 —— 「已经发生了什么？」面向已存在的历史提交：左侧泳道图与提交列表呈现全部提交，详情面板查看某次提交的说明与文件差异；配合分支/作者/时间段筛选、检出、reset、fetch / pull / push。以浏览和远端操作为主，不改动工作副本内容。
  • 工作副本 —— 「接下来要提交什么？」面向尚未提交的本地更改：左侧文件状态列表勾选暂存，右侧查看选中文件此次的差异，底部撰写（或让 Copilot 生成）提交信息并执行提交 / 推送 / 修订。即 Sourcetree 的「File Status / 工作副本」页，本方案新增。

提交流程把两者串成闭环：在工作副本完成提交后，新提交立即出现在提交图中。两个视图是同一 Webview 内的兄弟 DOM 节点，切换只切 display，不销毁、不重建——提交图的选择/滚动/筛选，与工作副本的草稿/选中文件/分组展开态，在切换间全部保留。

决策：提交界面采用「独立主视图」而非底部抽屉 / 模态对话框。理由：① diff 预览需要大尺寸可读空间，抽屉高度受限；② 模态对话框打断操作流，违背「直达交互」原则；③ 挂到现有详情面板位置会与「选中提交的详情」语义冲突。工作副本视图下自动隐藏左侧分支侧栏（220px），把空间让给文件列表与 diff；仓库切换不受影响（工具栏本就有仓库下拉）。

2.2 核心心智模型

  • 已暂存 = 将进入下一次提交的内容。左栏勾选状态即 git index 状态，所见即所得。
  • 同一文件可能同时出现在两个分组（已暂存一部分、工作区又改了）：两行各自独立勾选、各自独立 diff（index↔HEAD 与 worktree↔index），与 Sourcetree 行为一致。
  • 右栏只显示当前选中文件此次的完整差异（HEAD ↔ 工作副本，已暂存与未暂存更改合并呈现；未跟踪文件显示为全新增）。不区分已暂存/未暂存、无页签，也不聚合多文件。

3.3 文件状态列表细节

  • 分组与排序：「已暂存」在上、「未暂存」在下（Sourcetree 同序）；组头可折叠（展开态持久化）；组内按路径字母序；每组计数实时更新。未跟踪文件（U）归入「未暂存」组。
  • 状态徽标：字母 + 语义色，与 VS Code SCM 惯例一致 —— M 修改、A 新增、D 删除、R 重命名（显示 old → new）、U 未跟踪。
  • 勾选即暂存（乐观更新）：点击复选框立刻勾选/移动分组（150ms 过渡高亮），同时发 git add / git restore --staged；失败则回滚 UI 并 toast 报错（含 git stderr 首行）。操作经 OpRunner 串行队列，与 fetch/push 自然互斥。
  • 右键菜单：见下图。丢弃为红色高危项，仅出现在「未暂存」行；「已暂存」行提供「取消暂存」。
  • 双态文件：同一路径在两组各有一行，互不影响；tooltip 注明「该文件另有已暂存的更改」。
  • 过滤框：对两组联通过滤（子串匹配路径），无结果时显示空提示；「全部暂存」在有过滤时仅作用于匹配项（菜单悬浮提示说明）。

3.4 Diff 预览（单文件 · 单视图）

  • 只显示选中文件此次的差异（v1.2 修订简化）：diff 区渲染当前选中文件 HEAD ↔ 工作副本的完整差异（该文件本次已暂存 + 未暂存更改的合并结果），命令为 git diff HEAD -- <path>。不区分已暂存/未暂存，无页签，除文件名与增删统计外不显示其他信息。点击左栏任意行即整体切换；无选中时显示空态「在左侧选择一个文件查看差异」。
  • 文件切换：文件头右侧 ‹ › 按钮在更改文件列表中逐个切换，无需来回点左栏。
  • 未跟踪文件预览：直接读文件内容渲染为「全新增」视图（文本 ≤1MB；二进制显示「二进制文件」占位），不改动 index。
  • 操作按钮：打开文件（编辑器）；VS Code 原生 diff（复用 gitboard: scheme：HEAD 版本 ↔ 磁盘文件）；复制路径；在资源管理器中显示（沿用原生 spawn 方案）。
  • 超大 diff：沿用现有 5000 行截断 + 「显示更多」策略；diff 结果按 path + HEAD sha 缓存，HEAD 未变且文件未再编辑时不重拉。
  • 与 AI 上下文的区别：AI 生成提交信息仍基于已暂存差异（git diff --cached，只送将进入下次提交的内容，见 §5.3）；预览区面向「看这个文件这次改了什么」，两者数据源独立、互不影响。

3.5 提交信息栏（单一输入框）

  • 结构（v1.2 修订：单一输入框）：操作行（AI 生成 / 模型 / 最近信息 / 首行字数）→ 唯一一个多行提交信息输入框 → 底行（提交后推送复选框 + 提交按钮组）。不再拆分 subject / body 两个输入；首行即摘要、空行后即正文（git 原生约定），placeholder 给出提示。整栏可折叠为一条 32px 窄条（点标题重新展开）。
  • 字符向导：仅对首行计数（38 / 50，超 50 变琥珀色）；正文 72 列软换行不强制。
  • 提交校验：已暂存为空且非「提交全部」时按钮禁用（tooltip 说明）；首行为空时聚焦并红框提示；合并冲突进行中（存在未解决路径）时禁用并提示。
  • 提交成功：toast 显示新提交摘要；提交图刷新并高亮新提交（不强制切回提交图视图）；信息栏按配置清空（默认清空）；「提交后推送」按勾选链式推送并沿用现有进度条。
  • 修订上次提交（amend）：从下拉进入，信息栏载入 HEAD 提交信息并出现琥珀色提示条：

3.6 AI 生成交互（Copilot）

三个状态：空闲 → 生成中（流式）→ 完成。生成结果直接落入唯一的提交信息输入框（非聊天面板），用户随手可改；模型输出首行即摘要、空行后即正文，与输入框约定一致。

3.7 状态、动效与空状态

  • 状态保持：视图切换用 display:none 保留两侧 DOM；信息草稿、选中文件、分组展开态、diff 模式全部在会话内保留；草稿另以 500ms 防抖写入 globalState（按仓库路径区分），Webview 被回收重建后自动恢复。
  • 动效：文件在两组间移动时 150ms 高亮渐隐；徽标数字变化轻微弹跳；AI 流式输入带光标闪烁。全部 <200ms，不拖慢操作。
  • 空状态：工作副本干净时显示居中提示与上次提交摘要，提供「拉取 / 推送」快捷按钮：

4. 功能规格

4.1 优先级总表

4.2 关键行为细则

暂存 / 取消暂存

  • 多选（Ctrl/Shift）后右键或 Space 批量操作；未跟踪文件勾选即 git add（等价其被纳入暂存）。
  • 「全部暂存」= git add -A；「全部取消」= git restore --staged .（有过滤时仅对匹配路径逐个操作，并提示数量）。
  • 操作期间行复选框禁点（同一行防抖），避免竞态；队列天然串行化。

提交 / 提交并推送

  • 信息经临时文件提交（os.tmpdir() 下随机名，用后即删），避免 argv 转义与换行问题；--cleanup=strip 去尾部空白。
  • 「提交并推送」= commit 成功后自动入队 push；任一失败即停并 toast（push 失败时提交已成功，明确提示）。
  • 「提交全部更改」= git add -A + commit，按钮始终可用（有任意更改时），避免用户被空暂存卡住。
  • hooks（pre-commit / commit-msg / husky）正常执行；失败时展示 stderr 摘要并提供「查看完整输出」。

AI 生成（行为）

  • 默认基于已暂存 diff；暂存为空时按钮文案变为「基于全部更改生成」并在确认后按未暂存内容生成（此时提示建议先暂存）。
  • 生成前自动加载工程指示文件（.copilot/、.github/，§5.7），以「MUST follow」小节注入提示词；生成完成的 meta 行注明已应用份数，tooltip 可见来源路径。
  • 生成完成自动 focus 到输入框末尾；重新生成覆盖前若用户已手改且非上次生成结果，弹轻量确认（行内，非模态）。
  • 生成失败（未登录 / 配额 / 超时）：信息栏下方显示错误行 +「重试」「换模型」；不弹模态。

5. GitHub Copilot 集成

5.1 能力来源与前置条件

  • 使用 VS Code Language Model API（vscode.lm.selectChatModels / model.sendRequest），该 API 自 VS Code 1.99（2025-03）起稳定；本次随功能将 engines.vscode 提升至 ^1.99（距当前已逾 17 个月，市场覆盖率安全）。
  • 前置条件：用户已安装并登录 GitHub Copilot。selectChatModels({vendor:'copilot'}) 返回空数组即视为不可用 —— AI 按钮整体隐藏，其余提交功能不受影响；监听 lm.onDidChangeLanguageModels 动态显隐。
  • 运行时特性探测（typeof vscode.lm === 'undefined' 兜底），理论上兼容老版本 VS Code 的降级路径仍保留。
账户分析（需求确认：直接使用当前 VS Code 登录的 Copilot 账户）——原生满足，无需任何改造：
  • 同一登录态：vscode.lm 的 copilot 模型由 VS Code 内置的 Copilot 服务提供，鉴权完全复用 VS Code 当前登录的 GitHub 账号（与日常使用 Copilot Chat 同一账号、同一订阅、同一配额池）。用户在本机 VS Code 登录 Copilot 后，本功能即刻可用。
  • 扩展零凭证：GitBoard 不需要、也不接触 PAT / API Key / OAuth 流程，不存储任何令牌；凭据生命周期全部由 VS Code 与 GitHub 认证会话管理。
  • 订阅与组织策略自动生效：账号档位（Free / Pro / Business / Enterprise）与组织策略（如可用模型限制、内容排除）自动体现在 selectChatModels 返回的模型清单中——模型下拉里出现的就是这个账号能用的，不会请求越权模型。
  • 配额按该账号计划计费：请求消耗账号的 Copilot 配额（premium requests / chat 额度），超额返回 429 —— 已按 §5.2 / §7.2 分类提示处理。
  • 登录状态联动：登出或订阅失效 → selectChatModels 返回空 → AI 入口自动隐藏；重新登录经 lm.onDidChangeLanguageModels 自动恢复。
结论：LM API 正是为「扩展复用宿主内 Copilot 登录」设计；若改走「直连 Copilot REST API」路线，反而必须自建 GitHub PAT 凭证管理（体验与安全性均差，已排除）。

5.6 核心代码形态（宿主侧）

// panel.ts —— AI 生成提交信息（流式转发给 Webview）
private aiCts?: vscode.CancellationTokenSource;

async aiGenerateCommitMessage(modelId?: string): Promise<void> {
  const models = await vscode.lm.selectChatModels({ vendor: 'copilot' });
  const model = modelId ? models.find(m => m.id === modelId) ?? models[0] : models[0];
  if (!model) { this.post({ t: 'aiError', data: { code: 'noModel' } }); return; }

  const ctx = await this.git.buildCommitContext(this.root);   // diff(截断)+文件统计+近10条+项目指示(§5.7)
  const prompt = buildPrompt(ctx, this.cfg.ai);               // 附录 A 模板

  this.aiCts = new vscode.CancellationTokenSource();
  try {
    const res = await model.sendRequest(
      [vscode.LanguageModelChatMessage.User(prompt)], {}, this.aiCts.token);
    for await (const chunk of res.text) {
      this.post({ t: 'aiChunk', data: { text: chunk } });      // Webview 流式填充
    }
    this.post({ t: 'aiDone' });
  } catch (e) {
    this.post({ t: 'aiError', data: classifyLmError(e) });      // auth | quota | canceled | error
  } finally { this.aiCts.dispose(); this.aiCts = undefined; }
}

5.7 项目指示文件：遵循 .copilot / Copilot 指示定义（v1.3 新增）

需求：调用 Copilot 生成提交信息时，若当前工程定义了指示文件（instructions），必须读取并遵守其中约定，再结合本次修改内容生成。

关键事实：vscode.lm 是裸语言模型 API，不会自动附加 Copilot Chat 在聊天层注入的指示文件（.github/copilot-instructions.md 等只对 Copilot Chat / Coding Agent 界面生效）。因此 GitBoard 必须自行扫描工程内指示文件并注入提示词——这正是本节的设计内容；效果上等价于"让 Copilot Agent 遵守同一套工程指示"。
  • 扫描位置（可选、存在即用，按优先级合并注入）：
    1. .copilot/ 目录下全部 *.md（按文件名排序）—— 工程自定义指示，最高优先；
    2. .github/copilot-instructions.md —— GitHub Copilot 官方指示文件（Chat / Coding Agent 通用约定）；
    3. .github/instructions/*.instructions.md —— Copilot 分域指示文件（含 applyTo front-matter；不做 glob 匹配，整篇注入并标注来源）。
  • 注入方式：作为 user prompt 的 # Repository custom instructions (MUST follow) 独立小节，位于风格样本之后、变更内容之前；每份内容带来源路径标注（见附录 A）。
  • 预算：单文件截断 4K 字符、合计 8K（截断时在提示词内注明「已截断」）；与 diff 预算（§5.3）独立核算，指示文件优先保量——它定义的是"必须怎么写"。
  • 缓存与刷新：按文件 mtime 缓存；每次生成前做一次轻量 mtime 检查（指示文件通常只有几份，开销可忽略），不引入实时 watch。
  • UI 呈现（极简，不打扰）：检测到指示文件时——✨ 按钮 tooltip 追加「已加载 N 份项目指示」；生成完成后的 meta 行显示「已遵循项目指示（.copilot/ 等 N 份）」；未检测到则完全无感、不占任何空间。
  • 开关：设置 gitboard.ai.useWorkspaceInstructions（默认开）可整体关闭读取。
  • 隐私：指示文件内容将随 diff 一并发送至 Copilot 服务，已并入 §5.5 首次确认文案。

  untracked: boolean;                       // '??'
}

}
