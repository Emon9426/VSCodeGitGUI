GitBoard 合并与冲突解决方案

文档版本：v1.3（需求，已审查 · 决议见 §8；v1.3 三审：回归三栏布局（我的-合并-他人），呈现清晰化，AI 保留） ·  目标产品版本：v0.10.x ·  日期：2026-08-23 ·  参考：IntelliJ IDEA 合并界面 / VS Code Merge Editor 交互范式

本文档定义 GitBoard 的代码合并与冲突解决功能：以三栏合并解决器（我的版本 – 合并版本 – 他人版本，IDEA / Beyond Compare 式块级交互、更清晰的呈现）为核心， 为 pull / commit / push 过程中出现的冲突提供主动引导 + 逐文件可视化解决的完整闭环， 并可选接入 AI 模型辅助解决复杂冲突。

1 背景：现状与差距

v0.8.0 已实现冲突「二选一」最小闭环：

  • 工作副本视图将 UU/DD/AA/AU/… 状态文件归入「冲突」独立分组，行内提供 我的 / 对方的 二选一按钮与组级全选（git checkout --ours/--theirs + add）；
  • 冲突全部解决且 MERGE_HEAD 存在时自动 commit --no-edit 完成合并；
  • 存在未解决冲突时提交被拦截（conflictBlock）。

差距（本次要补齐的能力）：

现状差距
只有"整文件二选一"，无法保留双方改动没有可视化合并界面，无法以合并后的代码为准（手动融合两侧/多冲突块逐块取舍）
冲突靠用户自己发现（切到工作副本视图才看到）pull/commit/push 触发冲突时无主动引导；push 被拒（non-fast-forward）只显示一段 stderr
二进制冲突与文本冲突同等对待二进制无法对照合并，也看不出差异，应只提供二选一+预览
rebase 场景（mergeKind=other）语义反转仅靠文案提示，完成后不能 --continuerebase/cherry-pick 冲突走不通完整闭环
没有"反悔"入口缺少 merge --abort / rebase --abort 中止能力
AI 仅用于生成提交信息未接入冲突合并场景

2 需求定义

编号优先级需求描述
R1P0 合并解决器（三栏）：我的版本 – 合并版本 – 他人版本 三栏并排（IDEA / Beyond Compare 式）——左右两栏只读对照、差异着色，中间"合并版本"栏即最终保存的结果，可自由编辑。每个冲突块就近提供快捷按钮：⬅ 用我的 / 用他人 ➡ / 两个都要 / 都不要 / ✦ AI 融合；左右栏块边提供 IDEA 式 « » 一键采纳箭头。冲突块全程以色块呈现，不暴露 git 冲突标记。AI 辅助合并保留（R7）。
R2P0 三种文件级解决策略：① 以我的代码为准；② 以远端的代码为准；③ 以合并后的代码为准（接受编辑后的合并结果，含 git 已自动合并无冲突的部分）。三者均需一键完成并暂存（git add）。
R3P0 冲突主动引导：pull 出现冲突、commit 被冲突阻塞时，自动切到工作副本视图并弹出冲突引导横幅，一键进入合并器；push 被拒（远端领先）时引导"先拉取再推送"，拉取后若冲突则无缝进入冲突流程。全部解决后自动完成合并/变基并提示结果。
R4P0 二进制文件：自动识别（含 \0 字节 / numstat 为 -）。不提供版本对照与"合并后为准"，只提供以我为准 / 以远端为准二选一 + 用系统程序打开预览。
R5P0 操作友好：进度可见（N/M 个文件待解决）、逐文件"解决并进入下一个"自动流转、整组批量策略、随时中止合并（恢复到操作前状态）、CRLF/编码保持、误操作可反悔（重新打开合并器改选另一侧）。
R6P1 rebase / cherry-pick 支持：ours/theirs 语义按场景自动反转并在界面上始终以语义标签（"我的"/"远端"）呈现；全部解决后自动 rebase --continue，若下一个提交仍有冲突则继续引导，直至变基完成。
R7P2 AI 辅助合并：对单个冲突块（或全部冲突批量）调用 VS Code 语言模型（现有 vscode.lm 通道），输入 base/双方版本，生成融合结果填入中栏对应块（紫色"AI 待审"色条）供审查-修改-确认；流式输出、可取消、无模型时隐藏入口。
明确不做：跨仓库批量合并、submodule 冲突解决、锁文件（.gitignore 外的 lock 类）特殊策略、强制推送入口。首版聚焦单仓库文本/二进制两类冲突的完整闭环。

3 典型场景走查

场景 A：pull 产生冲突（最主路径）

① 拉取点工具栏 Pull，按默认策略执行
→
② 检测到冲突自动切工作副本视图，顶部弹出冲突横幅「发现 3 个文件冲突」
→
③ 逐个解决点「逐个解决」进入三栏合并器，逐块点「⬅用我的 / 用他人➡」或两侧 « » 箭头采纳，拿不准的可 ✦AI 融合或直接在中栏改
→
④ 完成合并最后一个文件解决后弹确认「N 个冲突已全部解决，完成合并？」（显示默认合并信息），确认后 commit --no-edit（决议 #2）

场景 B：push 被拒（non-fast-forward）

① 推送点 Push
→
② 事前拦截检测到本地落后远端（behind>0）：弹确认「远端有 N 个新提交，建议先拉取」
[拉取并推送] [仅拉取] [取消]
→
③ 拉取按默认策略 pull；若失败被拒（fetch first / rejected）同款引导兜底
→
④ 分流无冲突 → 自动继续推送；有冲突 → 进入场景 A 的冲突横幅（推送暂停），冲突全部解决并完成合并后弹确认条「继续推送？」，由用户点击确认（决议 #3）

场景 C：提交时存在未解决冲突

① 提交Commit 面板点「提交」
→
② 引导而非报错存在冲突时不抛 conflictBlock 硬错误，而是自动展开冲突横幅并高亮第一个冲突文件，提示「先解决 N 个冲突再提交」
→
③ 解决完成合并完成后停留在提交面板，提交信息草稿保留，用户直接提交

4 总体方案

4.1 冲突拦截与引导 P0

三个触发点的判定与动作：

触发点判定动作
pull 后 pull 结束（无论 opResult 成败）后刷新 workState：conflicts.length > 0；或 stderr 含 CONFLICT 自动切工作副本视图（showWork）→ 推送冲突横幅（见 4.2）+ notify 提示音级提醒
commit 前 点「提交」时 S.work.state.merging === true 不执行提交；自动切工作副本视图 + 弹横幅 + 高亮首个冲突行（替换现有 conflictBlock 纯报错）
push 前/后 事前：RepoState 中 HEAD 分支 behind > 0（数据已有）；事后兜底：stderr 匹配 non-fast-forward|fetch first|rejected 三选一确认（拉取并推送 / 仅拉取 / 取消）；「拉取并推送」= pull → 无冲突自动 push、有冲突暂停进入横幅流程，冲突解决并完成合并后弹确认条由用户确认续推（决议 #3，不自动续推）

4.2 冲突横幅（工作副本视图顶部）P0

替代"用户自己找冲突"：只要 merging 为真，工作副本视图顶部常驻一条横幅，直至冲突清零或中止。

MOCK 1冲突横幅 —— 自动出现，聚合所有入口动作
⚠ 合并进行中 · 3 个文件待解决 （本地 HEAD ↔ origin/feature-x，默认策略 merge） 逐个解决（打开合并器） 全部以我为准 全部以远端为准 中止合并
↑ 横幅下方即现有工作副本文件列表；「冲突」分组行内保留二选一快捷按钮，点击行本身改为打开合并器（原为看 diff）。

4.3 合并解决器（三栏：我的 – 合并 – 他人）P0

呈现演变：初稿三栏（v1.0，中栏暴露 git 标记）→ 逐块向导（v1.2）→ 三审定稿（v1.3）：保留经典三栏布局，交互参考 IDEA / Beyond Compare，呈现上做清晰化改造。布局：

⬅ 我的版本只读对照 · 蓝色高亮我的改动 · 块边「»」一键采纳
⬇ 合并版本可编辑 · 最终保存的就是它 · 黄块=待处理，绿块=已解决
他人版本 ➡只读对照 · 绿色高亮他人改动 · 块边「«」一键采纳
一句话心智模型：「中间栏就是最终结果——点两侧按钮把想保留的代码搬进来，或直接在里面改；全部黄块变绿，点完成合并。」

相对初稿（v1.0）的五个清晰化改造——解决"难以理解"的反馈根源：

  1. 中栏不显示 <<<<<<< 等冲突标记（初稿最大障碍）：冲突块渲染为黄色区块，块内直接显示该块当前结果（初始=我的版本），来源用左缘色条标识（蓝=来自我的 / 绿=来自他人 / 灰=已手动修改 / 紫=AI 待审）；
  2. 按钮就近放：每个黄块头部一行操作条「⬅ 用我的 / 两个都要 / 用他人 ➡ / 都不要 / ✦ AI」，不藏在顶栏或底部；左右栏块边的 IDEA 式 « » 箭头点一下即采纳该块；
  3. 栏头大白话 + 角色徽标：「我的版本（只读 · 本地 HEAD）」「合并版本（最终保存的就是它 · 可编辑）」「他人版本（只读 · origin/feature-x）」；
  4. 状态色语义全局固定并常驻图例：黄=待处理冲突、绿=已解决、蓝/绿高亮=两侧各自改动、灰=三栏相同的公共部分（弱化显示）；
  5. 右侧导航细条（Beyond Compare 式 minimap）：整根细条映射全文件，黄点/绿点=冲突分布，蓝框=当前视口，点击跳转——比"上一处/下一处"更直观地回答"还剩几处、都在哪"。

  • 1 采纳整块：点左栏块边「»」或中栏块头的「⬅ 用我的」，该黄块立即替换为我的版本并变绿（resolvedbar 可「重选」）；右栏「«」同理。「两个都要」= 我的在前、他人在后（决议 #6）；「都不要」= 删除该块（两侧改动都放弃）。

决策（决议 #1 + #8 三审定稿）：内嵌 Webview 自绘（VS Code 原生 Merge Editor 无公开 API，放弃）。布局为经典三栏我的 – 合并 – 他人（IDEA / Beyond Compare 交互），叠加五个清晰化改造（无标记呈现 / 按钮就近 / 大白话栏头 / 固定色语义 / 冲突 minimap）。提供「在 VS Code 打开对照」逃生口（ours/theirs 虚拟文档 + vscode.diff，机制已有）。

4.4 三种文件级解决策略 P0

策略行为git 语义
以我的代码为准整文件取语义"我的"一侧，不打开编辑checkout --ours/--theirs（按场景映射，见 4.6）+ add
以远端的代码为准整文件取语义"远端"一侧同上，另一侧
以合并后的代码为准接受中栏"合并版本"的最终内容（= git 自动合并成功的部分 + 你在各冲突块上的采纳/手改）中栏内容写回工作副本文件 + add（点「全部解决，完成合并」时执行）

三个入口层级一致：块级（块头操作条 + 左右栏 « » 箭头 + 中栏直接编辑）、文件级（顶栏「整文件快选 ▾」）、组级（横幅「全部以我为准/全部以远端为准」，弹确认显示文件数）。「两个都要」= 我的在前、他人在后（IDEA 默认，决议 #6）。

4.6 rebase / cherry-pick：语义反转 P1

核心坑：rebase 时 git 的 --ours 是变基基底（远端）、--theirs 才是本地正在重放的提交，与 merge 恰好相反。界面上永远只显示语义标签（"我的"/"远端"），语义→git 参数的映射由扩展侧完成：
场景（mergeKind）判定「我的」对应「远端」对应全部解决后
merge.git/MERGE_HEAD 存在:2 / --ours:3 / --theirs弹确认后 commit --no-edit（决议 #2）
rebase.git/rebase-merge 或 rebase-apply 存在:3 / --theirs:2 / --ours弹确认后 rebase --continue，若后续提交再冲突则循环引导（横幅显示"第 k 个提交"）
cherry-pick / revert.git/CHERRY_PICK_HEAD 等按 merge 同向（:2）:3弹确认后 --continue（无 editor）

4.7 中止与完成 P0

  • 中止合并：横幅/合并器内「中止合并」→ 二次确认（说明将丢弃所有取舍、恢复到合并前）→ merge --abort / rebase --abort（按 mergeKind 分派）→ 刷新并提示"已取消，工作副本已还原"。未跟踪文件不受影响。
  • 完成（弹确认，决议 #2）：最后一个冲突解决并暂存后不自动提交，弹出确认框——merge 场景：「3 个冲突已全部解决，完成合并提交？」+ 默认合并信息（MERGE_MSG 首行）预览 + [完成合并] [稍后自己提交]；rebase 场景：「继续变基？（第 2/4 个提交）」+ [继续变基] [稍后]。确认后执行对应完成命令（见 4.6 表），成功 → 绿色提示 + 图形/工作副本刷新；失败（如 hooks 拒绝）→ 显示 stderr 并保留现场。「稍后」时横幅保持常驻（仍 merging=false 但 MERGE_HEAD 在，显示"待完成合并"状态与 [完成合并] 按钮），用户也可随时在提交面板自行提交。
  • 拉取并推送流程的续推（决议 #3）：处于「拉取并推送」链条且冲突已解决、合并已确认完成后，显示确认条「冲突已解决并完成合并，继续推送？」+ [推送] [暂不]（复用 v0.8.0 提交后推送询问条的交互形态），由用户点击触发，不自动续推。
  • 反悔：已解决的文件仍显示在「已暂存」组（M 状态）；重新产生冲突的途径（再次 pull 等）以外，提供文件右键「重新解决冲突」不做（git 已无冲突态，语义不成立）——仅在同一合并会话内（冲突未清零时）允许对尚未解决的文件反复改选。

4.8 AI 辅助合并 P2

  • 入口：① 冲突块头操作条「✦ AI」——融合当前块；② 顶栏「AI 融合此文件」——对该文件全部未解决块生成；③ 横幅「AI 解决全部」（批量，逐文件串行，进度可取消）。依赖 aiEnabled 探测，无模型隐藏；模型选择复用现有提交信息功能的模型选择器与 aiLanguage 配置，不新增独立配置项（决议 #4）。
  • 输入：base（:1）、我的（:2/:3 按语义）、远端，各带少量上下文（文件路径、语言、块序号）。要求模型只输出融合后的代码（无解释、无 Markdown 围栏），复用现有 vscode.lm 流式通道（aiChunk 事件族扩展 merge 场景）。
  • 安全底线：AI 输出只填入中栏对应冲突块（紫色"AI 待审"来源色条，仍属未解决状态），绝不自动标记已解决/自动暂存；用户审查/手改（色条变灰）或点块头确认采纳后计入已解决；提供「撤销 AI 结果」；批量模式逐文件生成后汇总「N 个文件已由 AI 融合，请逐个审查」，由用户逐个确认。

5 技术设计

5.1 协议与命令扩展

新增 Webview 命令（WVCommand）：

merge.session      { path }        -> MergeSession | MergeSessionBinary | MergeSessionTooLarge
merge.resolve      { path, side: 'mine' | 'theirs' }          // 语义侧二选一（含 add）

merge.continue     {}                                         // rebase/cherry-pick --continue
merge.aiSuggest    { path, blockIndex? }                      // AI 融合（流式，见下）
merge.aiCancel     {}

新增事件：

{ t: 'mergeAiChunk'; path: string; blockIndex?: number; text: string }   // 流式增量
{ t: 'mergeAiDone';  path: string; blockIndex?: number }
{ t: 'mergeAiError'; path: string; code: 'noModel'|'auth'|'quota'|'canceled'|'error'; message? }
{ t: 'conflictBanner'; count: number; merging: boolean }                 // 拦截引导（也可由 workState 派生）

数据模型（models.ts）：

interface MergeSession {
  path: string;
  kind: 'merge' | 'rebase' | 'cherry-pick';   // 标签与完成动作分派
  labels: { mine: string; theirs: string };   // 语义标签（"我的版本 · 本地 HEAD" / "远端版本 · origin/feature-x"…）
  rebaseStep?: { current: number; total: number };
  binary: false;
  base?: string;      // :1 原始内容（AI 输入用；ADD/DELETE 侧可为空）
  mine: string;       // 语义"我的"完整内容
  theirs: string;     // 语义"远端"完整内容
  result: string;     // 工作副本当前内容（含冲突标记；扩展侧解析为冲突块数组推给三栏 UI）
}
// 二进制：{ path, binary: true, mineSize, theirsSize, mineDate, theirsDate, deletedSide?: 'mine'|'theirs' }
// 过大：{ path, tooLarge: true, lines: number, bytes: number, limit: { lines: 16000, bytes: 2MB } }  → UI 显式警告 + 降级三选一 + "用 VS Code 打开"

5.3 冲突块解析、中栏状态与写回

  • 解析：对 result 按 <<<<<<< 、=======、>>>>>>> 三标记切分为冲突块数组（兼容 ||||||| diff3 段，只读忽略），每块记录我的段/他人段文本与行号区间。git 标记只在扩展侧出现，三栏 UI 永不显示。
  • 中栏模型：中栏 = 公共部分按序 + 各冲突块的当前结果；每块状态为 { 来源: mine|theirs|both|none|manual|ai, 文本, 已解决 }。块按钮/箭头只改对应块；块内手改后来源转 manual；点「全部解决」要求所有块已解决。同一合并会话内已解决块可「重选」。
  • 三栏同步滚动：按公共行（灰色行）锚点对齐——三栏公共部分行文本相同，滚动任一栏时以锚点行推算其余两栏 scrollTop；首版允许以冲突块为锚点的近似对齐，不追求逐行 diff 算法。
  • 写回保真：解析时记录行尾风格（CRLF/LF）与 BOM，merge.save 原样保留；内容一律 UTF-8 读写（与现有 diff/未跟踪预览一致）。

5.4 边界与安全

边界处理
超大文件任一侧 > 16000 行或 > 2 MB（阈值较初稿扩倍，决议 #5）→ MergeSessionTooLarge，显式警告提示：「src/generated/api.d.ts 共 2.3 万行（3.5 MB），超过合并编辑器上限（16000 行 / 2 MB），已降级为三选一。可用 VS Code 手动合并后再点『已手工解决』」——不静默降级；降级为文件级三选一 + 「在 VS Code 中打开」手动编辑后回来点「已手工解决（暂存）」。大文件无渲染压力：三栏各自窗口化渲染（只渲染视口 ± 缓冲行，复用提交列表虚拟行池经验），DOM 与文件行数解耦。
非 UTF-8 / 疑似乱码内容含非法 UTF-8 序列比例超阈值 → 提示"该文件非 UTF-8，建议用外部合并工具"，仅提供二选一
一方删除（DD/UD/AU）合并器显示"对方已删除此文件"：保留我的版本 / 采纳删除（git rm）二选一
重命名+冲突（R+U）按冲突路径处理，行内显示原路径提示；不提供两侧改名选择（首版）
合并器打开期间外部修改「标记已解决」前用文件 mtime+size 比对，变化则提示"文件已被外部修改"并刷新会话
多仓库 / 面板重建会话不持久化：Webview 回收后重进合并器重新读取（取舍未暂存的内容会丢——「标记已解决」即落盘，风险窗口小；横幅常驻提醒）
AI 输出含围栏/解释剥取首个代码围栏内容；解析失败则标记"AI 结果可疑"要求手改

7 风险与对策

风险对策
中栏可编辑的输入法/光标/快捷键复杂度首版中栏行内编辑用受控 textarea 叠加行号槽（点击冲突块进入编辑态），块按钮/箭头为纯按钮操作不受影响；验证后再升级自绘行组件
单个冲突块两侧都很长（数百行）块内行区限高（约 40% 视口高）内部滚动，minimap 同步反映；不影响其他块与主流程
rebase 多提交连续冲突让用户困惑横幅/合并器顶栏显示「变基进行中 第 2/4 个提交」，每步完成后自动进入下一步，不要求用户理解 --continue
AI 合并质量不稳定破坏代码绝不自动暂存/自动标记已解决（只进中栏紫色待审块 + 一键撤销）；批量模式逐个人工确认
「拉取并推送」链条中途失败定位难沿用 v0.9.2 进度行：拉取→合并→推送 三段进度分别播报，失败停在出错的段落并显示 outputTail

8 审查决议（2026-08-23，全部确认）

#问题决议（已并入正文）
1合并器内嵌 vs 原生内嵌自绘（§4.3）。VS Code 原生 Merge Editor 无公开 API，放弃；保留「在 VS Code 打开」逃生口。
2全部解决后自动完成合并？弹确认（§4.7）：merge 场景显示默认合并信息预览 + [完成合并]/[稍后自己提交]；「稍后」时横幅保持"待完成合并"状态可随时一键完成。
3「拉取并推送」冲突解决后续推？用户点击确认续推（§4.7）：完成合并后弹确认条 [推送]/[暂不]（复用 v0.8.0 推送询问条形态），不自动续推。
4AI 融合模型配置复用现有模型选择器与 aiLanguage（§4.8），不新增独立配置项。
5大文件阈值与超限行为扩倍至 16000 行 / 2 MB；三栏各自窗口化虚拟渲染（视口 ± 缓冲行），大文件无渲染压力（§5.4/§7）；超限显式警告报错（含实际行数/体积、上限值、降级说明与手动合并指引），不静默降级。
6「两个都保留」顺序我的在前、远端在后（§4.4，IDEA 默认）。
7合并解决器 UI 难以理解（v1.2 二审）~~三栏 → 逐块向导卡片~~ （已被决议 #8 取代）：v1.3 三审用户定稿回归三栏。
8合并解决器 UI 定稿（v1.3 三审）回归三栏「我的版本 – 合并版本 – 他人版本」（§4.3），交互参考 IDEA / Beyond Compare（块级采纳按钮 + «» 一键箭头 + 中栏可编辑 + 冲突 minimap），叠加清晰化改造：中栏不显示 git 冲突标记（黄块 + 来源色条呈现）、按钮就近放块头、大白话栏头角色徽标、固定色语义图例、右侧冲突分布导航条。AI 合并保留（块级 ✦AI / 整文件 AI / 横幅批量，R7·P2）。
