GitBoard 文件夹移动与历史保留方案
—— 独立「文件历史」页 · 可执行需求文档

文档版本：v1.4（五审稿 · 可执行） ·  目标产品版本：v0.14.0（P0）/ v0.14.x（P1） ·  日期：2026-08-29 ·  实测环境：Git 2.49.0.windows.1（累计 20 项实验） ·  配套 UI 预览：GitBoard-文件历史页预览.html（可交互：双视图 / 地址栏 / 多选 / 宽度拖拽 / 四场景）
修订记录： v1.0（一审稿）主界面筛选条方案 → v1.1（二审稿）重构为独立文件历史页（树/文件夹双视图 + 信息/预览/历史三段） → v1.2（三审稿）定案双视图/取消预览/移除路线 B，细化为可执行文档 → v1.3（四审稿）按用户反馈增补：左区宽度拖拽记忆（R9）、多选与删除/移动/重命名独立按钮（R10）、Win11 式地址栏（R11）、确认重命名与移动同机制（§4.4，第 20 项实测） → v1.4（五审稿，本版）细节定稿： ① 详细信息视图每一列可拖拽调宽并记忆（列边界手柄，悬停蓝色高亮）；② 移除选中行的单元格虚线描边——选中效果为纯色高亮，行内不出现任何竖向分割线（多选锚点不再有视觉标识）。

本文档定义 GitBoard 的文件历史页：以独立页面承载「浏览仓库文件 → 查看文件/文件夹的完整提交历史（跨移动跟随）→ 版本级操作（详情 / 打开指定版本 / 任意两版本比对）→ 引导式移动（git mv）」的完整闭环。 核心承诺：文件夹从 A 移动到 B/A 后，在 B/A 仍能看到 A 时期的全部提交，且不改写任何历史、对远端与协作者零影响。

1 背景与根因

场景：日常工作在文件夹 A 中持续提交产出；完工后移动到 B/A 归档。 移动后按 B/A 查看历史时，「看不到」A 时期的提交。

根因（决定技术路线的关键认知）：提交记录从未丢失。Git 每个提交都是全仓库快照，A 时期的提交完好地在历史链中； 「消失」是因为按路径过滤时，旧提交中的路径（A/…）匹配不上新路径（B/A）。 git mv 与 rename 检测只影响差异展示，不会改写旧提交中的路径。

技术路线（定案）：查询合并显示——不改任何提交、commit hash 不变、正常 pull/push、协作者零影响、随时可关闭跟随。 移动操作以 git mv + 「纯移动单独成提交」引导保证 rename 检测 100% 命中，为查询跟随提供可靠数据基础。

3 技术可行性验证（实测）

立项前在临时仓库完成三轮共 19 项实验（Git 2.49.0.windows.1；脚本留存于 %TEMP%/gitgraph-move-verify*.sh）。核心结论：

实验结果对方案的意义
git log -- B/A（按新路径过滤）只见移动后复现用户痛点
git log --diff-filter=R -M -- B/A空pathspec 过滤先于 rename 配对：单查新路径无法发现旧路径——必须换查法
文件级：git log --follow --name-status -- B/A/d1.md一次拿全右区主数据源：每条提交自带当时路径，R100 行带双端路径；两次移动链完整
目录级：边界提交 show -M（无 pathspec）反查旧前缀迭代链式闭环目录历史跟随算法可行（§4.4）
两版比对：git diff sha1:A/d1.md sha2:B/A/d1.md正确blob 级跨路径比对可行；stat 显示 {A => B/A}/d1.md 移动感知格式
多 pathspec git log -- B/A A全量目录历史合并显示（OR 语义）
移动 + 内容大改同一提交（含降阈值 20%）rename 丢失「纯移动单独成提交」是硬性实践 → R6/R7 引导设计的依据
50 文件目录移动 + 双 pathspec50 条 R100规模无压力（实现仍加 diff.renameLimit=10000）
路径 B/A[1]：裸 pathspec vs :(literal)literal 安全pathspec 一律 :(literal) 前缀
中文路径 git show HEAD:B/A/说明文档.md 与 blob diff正常executor quotepath=false + diff 头过 unescapeGitPath（v0.13.3 已有）
重命名：git log --follow --name-status -- 新名（同目录改名仓库）重命名前历史完整第 20 项实验：改名 需求草稿.md → 需求说明.md 后，按新名查询返回全部 5 条提交（含改名前 2 条，当时路径为旧名）；R100 行记录改名事件；重命名前最早版本 blob 比对有效——重命名与移动同机制，跟随对二者同样生效
结论：页面所需的全部 Git 能力实测通过，方案可行。UI 交互见配套预览页（已按三审稿更新并浏览器验证）。

4.1 页面框架与视图切换

  • 工具栏视图分段：⎔ 提交图 / ☰ 纯提交 / ▣ 工作副本 / 🗂 文件（第四段新增，选中态与其他段一致）。

4.4 历史跟随移动（算法）

文件级（右区主路径，单命令）

git log --follow --name-status -M --format="%H%x00%h%x00%an%x00%at%x00%s" -- ":(literal)<path>"
# 输出：每条提交 + 一行该文件的状态（M/A/R100 old new）→ 一次往返得到：
#   提交列表、每条提交的"当时路径"（M/A 行的路径 / R 行的新路径）、移动事件（R 行）、路径链
  • 时期归属：按 R 行切分路径段；首条（最早）路径段即创建路径。
  • 比对操作直接取两行的 sha + 当时路径，无需二次查询。

重命名与移动是同一机制（补充确认）

用户补充问题：重命名的文件能否取到重命名前的历史提交记录？——能，且无需任何额外机制。 在 Git 中，「同目录改名」与「跨目录移动」都是路径变更，统一记录为 R 状态（rename）条目； --follow 对二者同样跟随。第 20 项实验（需求草稿.md → 需求说明.md 同目录改名 + 叠加目录移动）实测：

$ git log --follow --name-status --format="COMMIT %h %s" -- B/A/需求说明.md
COMMIT 837dba8 移动 A → B/A
R100    A/需求说明.md      B/A/需求说明.md
COMMIT 79590f1 更新需求说明
M       A/需求说明.md
COMMIT acbc61b 重命名：需求草稿 → 需求说明
R100    A/需求草稿.md      A/需求说明.md      # ← 改名事件，双端路径齐全
COMMIT bfd8a96 修改草稿
M       A/需求草稿.md                          # ← 重命名前的历史，按当时旧名返回
COMMIT 59a45dd 创建需求草稿
A       A/需求草稿.md

$ git diff 59a45dd:A/需求草稿.md HEAD:B/A/需求说明.md --stat   # 重命名前最早版 ↔ 当前版
... | 2 ++                                                        # blob 比对有效 ✓

UI 呈现：改名提交同样显示为里程碑行（⇢ 需求草稿.md → 需求说明.md），旧名时期的提交带时期徽标（当时文件名）， 文件头链徽标为 需求草稿.md → A/需求说明.md → B/A/需求说明.md； 跨改名/跨移动的两版本比对均取各自当时路径，blob diff 正确。本页的「重命名（F2）」操作即同目录 git mv， 同样引导「纯重命名单独成提交」保证 R100 识别。（演示见预览页：历史列表含两个里程碑行与旧名时期徽标。）

目录级（链反查，选中文件夹时）

S = [ ":(literal)"+dir ];  P = dir;  chain = [ dir ]
repeat ≤ 8 轮（环/深度防护）:
    E = git log --format=%H -- <S> 的最后一条        # 边界提交（最早涉及）
    if E 不存在: break
    R = git show -M --name-status --format= E 中新路径以 "P/" 开头的 R 条目   # 无 pathspec！
    if R 为空: break                                 # 链终止（普通创建）
    oldPrefix = 旧路径公共前缀（覆盖率 ≥ 80% 投票，不足则 break + partial 标记）
    S += ":(literal)"+oldPrefix;  P = oldPrefix;  chain.unshift(oldPrefix)
# 目录历史: git log <排序参数> -- <S...>（多 pathspec OR）+ 按段边界 sha 标注时期
  • 成本：每轮 1 次纯 hash log + 1 次单提交 show；结果按「仓库+路径」缓存，新提交失效。
  • 降级：链断裂（移动+大改混提交、部分拆分）时显示当前路径时期 + 链徽标 tooltip 说明原因。

4.5 文件操作：移动 / 删除 / 重命名 与手动移动补救

操作交互入口语义与保障
移动命令条「✂ 移动到…」按钮（多选批量）/ 右键菜单 / VS Code 资源管理器右键直达原生目录选择 → git mv 入队（多选逐项执行）→ 横幅引导纯移动单独成提交（预填 chore: 移动 A → B/A）
删除命令条「🗑 删除」按钮（多选批量）/ 右键 / Del确认弹层（列明 N 项）：已跟踪 → git rm（进入待提交状态，提交前可恢复）；未跟踪 → 磁盘删除；删除后刷新树
重命名命令条「🗎 重命名 F2」（仅单选）/ 右键输入新名 → 同目录 git mv → 引导纯重命名单独成提交（预填 chore: 重命名 旧名 → 新名）；重命名前后历史自动跟随（§4.4）
前置校验仓库归属 / 目标已存在同名 / 嵌套移动（A → A/sub）/ 重名冲突 / 工作副本不干净时确认

为何强引导纯变更提交：实测证明「移动（或重命名）+ 大改内容」同提交会使 rename 检测彻底失效（相似度过低，降阈值也无法恢复）， 历史跟随随之中断；纯变更（内容零改动）的 R100 识别是确定性的。手动移动补救（R7）：系统资源管理器拖动后， 工作副本出现「同前缀批量 D + 同文件名批量未跟踪」时横幅提示（复用现有横幅交互），一键按移动 stage 并引导纯移动提交。

5.4 解析与路径安全

  • 新 parseFileLog()（parse.ts）：pretty 行（NUL 分隔五字段）+ name-status 行状态机；R 行 R100<TAB>old<TAB>new 直接映射 oldPath/path——与现有 parseFiles() 的 R 解析同构，负 token .match()（Mimosa 约束，勿用 .exec(）。
  • pathspec 一律 :(literal)；executor 参数数组不经 shell（免注入）。
  • 中文路径：executor 公共参数 core.quotepath=false；diff 输出头与 stat 行路径过 unescapeGitPath（v0.13.3 已有）。
  • blob 语法 sha:path：sha 固定 40 位十六进制；路径含 :/空格时引号包裹。
  • 只读 tab URI：gitboard-hist:<sha>/?p=<encodeURIComponent(path)>，避免路径与 authority 混淆。

5.5 边界与风险

场景行为 / 对策

9 评审确认点

  1. 默认视图：预览页以详细信息视图为默认（信息密度高、贴近资源管理器习惯）；如偏好文件夹视图默认请指出（一个常量切换）。
  2. 日期格式：详细信息视图「修改日期」采用 2026/8/29 09:12 绝对格式（资源管理器习惯）；如偏好相对时间可切换，已有 dateFormat 设置先例可复用。
  3. 详情展开方式：当前设计为「点击行 / ⓘ 就地展开」；如偏好仅 ⓘ 按钮触发（避免误触）请指出。
  4. 删除语义：已跟踪文件 = git rm（待提交，可恢复）；如偏好「移入回收站」（Electron 式 trash，VS Code 扩展 API 有 workspace.fs.delete 但无回收站）请指出，实装为 git rm + 确认弹层。
  5. 地址栏打开文件的默认行为：输入文件路径回车 = 选中（联动历史）+ 编辑器打开；如偏好只选中不打开请指出。
